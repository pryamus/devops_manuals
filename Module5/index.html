Compose → Kubernetes (k3d) → Helm → CI/CD

Стек: Python/Flask + PostgreSQL + Nginx

Ожидаемый результат: работающее приложение, развёрнутое тремя способами, с автоматическим пайплайном CI/CD

Этапы выполняются в два захода.

Заход 1 (локально на виртуалке): этапы 0–5 и 7 — всё разворачивается вручную и проверяется в браузере и через curl. Требуются только Docker, kubectl, k3d и Helm. Заход 2 (CI/CD): этап 6 — GitHub Actions, этап 6Б — GitFlic. Достаточно пройти один из двух (6Б выполняется целиком на этой же виртуалке: конвейер крутит собственный агент, GitHub-аккаунт не нужен). Выполняется отдельно, когда проект уже отработан локально и выложен в репозиторий. Этапы 6/6Б и Приложение A можно пропустить при локальном прогоне — остальные этапы от них не зависят.

0.5 Установка lazydocker

lazydocker — TUI-оболочка поверх Docker: в одном окне видно все контейнеры, их логи, потребление ресурсов, healthcheck-статус; оттуда же можно перезапустить контейнер или зайти внутрь shell'ом. Особенно удобно в этапах 1–3, где приложение живёт из трёх контейнеров.

Ставится из binary release GitHub (не через apt):

LAZYDOCKER_VER=0.25.2   # актуальную версию смотрите в Releases проекта

curl -L -o /tmp/lazydocker.tar.gz \
  "https://github.com/jesseduffield/lazydocker/releases/download/v${LAZYDOCKER_VER}/lazydocker_${LAZYDOCKER_VER}_Linux_x86_64.tar.gz"

mkdir -p /tmp/lazydocker
tar -xzf /tmp/lazydocker.tar.gz -C /tmp/lazydocker

sudo mkdir -p /usr/share/bin
sudo install -m 755 /tmp/lazydocker/lazydocker /usr/share/bin/lazydocker

rm -rf /tmp/lazydocker.tar.gz /tmp/lazydocker

lazydocker --version

/usr/share/bin — нестандартное место для бинарника (обычно используют /usr/local/bin), и каталога может не быть — mkdir -p решает это. Если which lazydocker ничего не находит, значит каталог не в PATH:

echo 'export PATH="/usr/share/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
which lazydocker

URL собран по шаблону релиза: lazydocker_<версия>_Linux_x86_64.tar.gz. Для ARM-машин используется файл _Linux_arm64.tar.gz.

Запуск из каталога проекта — он подхватит docker-compose.yaml и покажет все три сервиса:

cd ~/todo-app
lazydocker                       # выход — Esc/q

import os
import time

import psycopg2
from flask import Flask, redirect, render_template_string, request, url_for

app = Flask(__name__)

DB_HOST = os.environ.get("DB_HOST", "db")
DB_NAME = os.environ.get("POSTGRES_DB", "todo_db")
DB_USER = os.environ.get("POSTGRES_USER", "postgres")
DB_PASSWORD = os.environ.get("POSTGRES_PASSWORD", "password")


def get_db_connection():
    """Подключается к БД, повторяя попытку, пока база поднимается."""
    for _ in range(30):
        try:
            return psycopg2.connect(
                host=DB_HOST, database=DB_NAME, user=DB_USER, password=DB_PASSWORD
            )
        except psycopg2.OperationalError:
            time.sleep(2)
    raise Exception("Не удалось подключиться к базе данных")


def init_db():
    conn = get_db_connection()
    cur = conn.cursor()
    cur.execute("""
        CREATE TABLE IF NOT EXISTS todos (
            id SERIAL PRIMARY KEY,
            task TEXT NOT NULL
        );
    """)
    conn.commit()
    cur.close()
    conn.close()


# На этом этапе шаблон лежит прямо в коде — на этапе 2 вынесем в файл.
HTML_TEMPLATE = """
<!DOCTYPE html>
<html lang="ru">
<head><meta charset="UTF-8"><title>ToDo List</title></head>
<body>
    <h1>Список задач</h1>
    <form action="/add" method="POST">
        <input type="text" name="task" placeholder="Новая задача..." required>
        <button type="submit">Добавить</button>
    </form>
    <ul>
        {% for todo in todos %}
            <li>{{ todo[1] }}</li>
        {% endfor %}
    </ul>
</body>
</html>
"""


@app.route("/")
def index():
    conn = get_db_connection()
    cur = conn.cursor()
    cur.execute("SELECT id, task FROM todos ORDER BY id DESC;")
    todos = cur.fetchall()
    cur.close()
    conn.close()
    return render_template_string(HTML_TEMPLATE, todos=todos)


@app.route("/add", methods=["POST"])
def add_todo():
    task = (request.form.get("task") or "").strip()
    if task:
        conn = get_db_connection()
        cur = conn.cursor()
        cur.execute("INSERT INTO todos (task) VALUES (%s);", (task,))
        conn.commit()
        cur.close()
        conn.close()
    # Обычная HTML-форма без JS: отвечаем редиректом, чтобы пользователь
    # увидел главную страницу с новой задачей.
    return redirect(url_for("index"), code=303)


if __name__ == "__main__":
    init_db()
    app.run(host="0.0.0.0", port=5000)

Важное отличие от исходных документов. Там обработчик /add возвращал jsonify(...), 201, а браузер после отправки обычной формы показывал пользователю сырой JSON вида {"status":"success"}. Здесь сразу сделан 303 See Other на главную — это корректное поведение для этапа без JavaScript. На этапе 2, когда появится AJAX, вернём JSON обратно.

Три решения, которых не было в исходниках:

  • убрано поле version: '3.8' — в Docker Compose v2 оно помечено устаревшим и печатает предупреждение при каждом запуске;
  • depends_on: db: condition: service_healthy вместо простого списка — depends_on без условия означает лишь «старт контейнера», а не готовность сервиса. С healthcheck Compose дожидается реальной готовности PostgreSQL, поэтому приложение не падает на первой попытке подключения;
  • ports: "5432:5432" для db — проброс порта базы на хост ([порт_на_хосте]:[порт_в_контейнере]). Внутри сети Compose веб-приложение ходит к БД по DNS-имени db, этот маппинг ему не нужен; он нужен вам: подключиться к базе с хоста (psql -h localhost -U postgres todo_db), покрутить данные через любой SQL-клиент или заглянуть в неё из lazydocker. В Kubernetes этапа 4 такой проброс не понадобится — доступ к БД идёт через ClusterIP-Service, а если нужен psql снаружи, используется kubectl exec.

2.3 Код приложения

В app/app.py измените три места:

  1. Импорт — вместо render_template_string используем render_template (шаблон теперь берётся из app/templates/):

return render_template("index.html", todos=todos)
  1. Маршрут /add — возвращаем JSON, потому что теперь его вызывает JS:
@app.route("/add", methods=["POST"])
def add_todo():
    task = (request.form.get("task") or "").strip()
    if not task:
        return jsonify({"error": "Missing task"}), 400

2.4 Переход на Gunicorn

Dockerfile:

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY app/requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install --no-cache-dir -r requirements.txt

COPY app/ .

EXPOSE 5000

CMD ["gunicorn", "--workers", "4", "--bind", "0.0.0.0:5000", \
     "--access-logfile", "-", "--error-logfile", "-", "app:app"]

Что здесь принципиально:

  • app:app — Gunicorn импортирует модуль app и берёт из него объект app; точки нет, потому что модуль называется app.py, как и сам пакет;
  • --access-logfile - и --error-logfile - — логи пишутся в stdout/stderr, а не в файлы. Это обязательное условие для docker logs и kubectl logs;
  • PYTHONUNBUFFERED=1 — иначе print() из приложения буферизуется и в логах появляется с задержкой;
  • --workers 4 — четыре процесса-воркера. Учтите следствие: init_db() при старте выполнится в каждом воркере (он вызывается при импорте модуля, а не в блоке if __name__ == "__main__" — иначе gunicorn таблицу бы не создал вообще), поэтому в финальной версии он защищён advisory-lock'ом (см. todo-app/app/app.py). Именно из-за этого на свежей базе таблица todos появляется автоматически — Compose-том postgres_data к этому моменту ещё пустой.

3.3 Nginx: маршрут на статику

nginx/nginx.conf:

events {}

http {
    include      /etc/nginx/mime.types;
    default_type application/octet-stream;

    server {
        listen 80;

        # Статику отдаёт сам Nginx, мимо Flask/Gunicorn.
        location /static/ {
            alias      /app/static/;
            expires    30d;
            access_log off;
        }

        location / {
            proxy_pass         http://web:5000;
            proxy_http_version 1.1;
            proxy_set_header   Connection "";
            proxy_set_header   Host              $host;
            proxy_set_header   X-Real-IP         $remote_addr;
            proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        }
    }
}

Ключевое слово — alias: оно отдаёт файлы напрямую из файловой системы контейнера, минуя Python. expires 30d добавляет браузеру заголовок кэширования, поэтому CSS скачивается один раз.

Тонкость с дублированием заголовков. В исходных документах здесь стояло expires 30d вместе с add_header Cache-Control "public, no-transform";. Nginx сам добавляет Cache-Control: max-age=2592000 от директивы expires, поэтому в ответе оказывалось два заголовка Cache-Control подряд. Поведение браузеров в таком случае не определено, поэтому в готовых файлах оставлен только expires.

Там emptyDir всегда пустой, и монтирование его на /app/static «затрёт» CSS, запечённый в образ. Разбор этого — в Приложении B.

Этап 4. Развёртывание в Kubernetes в k3d

Цель: перенести ту же архитектуру в Kubernetes. Ключевое отличие от Docker Compose — вместо отдельных контейнеров web и nginx появляется один Pod с двумя контейнерами, разделяющими сетевой namespace и файловую систему.

Сначала доведите приложение до финального вида — скопируйте из todo-app/ папку app/, а также Dockerfile, docker-compose.yaml, nginx/nginx.conf. Остановите Compose, чтобы он не занимал порт 80:

docker compose down          # без -v: тома сохраняются, данные БД не пропадут

4.1 Подготовка образа

Актуальный Dockerfile (в готовых файлах корневой, из todo-app/):

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY app/requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install --no-cache-dir -r requirements.txt

COPY app/ .

EXPOSE 5000

     "--access-logfile", "-", "--error-logfile", "-", "app:app"]

Два отличия от ранних этапов и от исходных материалов:

  • RUN --mount=type=cache,target=/root/.cache/pip ... — кэш pip вынесен в постоянный кэш-том BuildKit. Слои Docker'а кэшируются как раньше, но если requirements.txt всё же изменился, пакеты, уже скачанные в прошлых сборках, берутся из кэш-тома, а не из интернета — пересборка ускоряется. Требуется BuildKit (в Docker Engine 23+ он включён по умолчанию);
  • нет curl и Docker-инструкции HEALTHCHECK — в исходных материалах этап 4 добавлял curl и HEALTHCHECK curl -fsS http://localhost:5000/healthz. В Kubernetes они не нужны: пробы готовности (readinessProbe / livenessProbe) kubelet выполняет по HTTP сам, HEALTHCHECK игнорируется, а лишние пакеты только утяжеляют образ. Проверять приложение будем пробами Kubernetes из k8s/03-web.yaml.

Сборка:

docker images | grep local-todo-web

Требуется BuildKit. Директива --mount=type=cache работает только с BuildKit. В свежих Docker Engine (23+) и в Ubuntu-пакете docker.io он включён по умолчанию, но если сборка падает сообщением the --mount option requires BuildKit или buildx component is missing, поставьте плагин:

  https://github.com/docker/buildx/releases/download/v0.17.1/buildx-v0.17.1.linux-amd64

Альтернатива — отдельный пакет docker-buildx из репозитория вашей ОС.

4.4 Изменения в app.py: маршрут /healthz и advisory-lock

Перед переходом в Kubernetes в app/app.py нужно внести два изменения. Без них этап 4 не заработает корректно:

  1. без маршрута /healthz не пройдут readinessProbe/livenessProbe из манифеста k8s/03-web.yaml, поды застрянут в 0/2 Running и не получат трафик через Service;
  2. без advisory-lock четыре воркера Gunicorn выполняют CREATE TABLE параллельно (см. п. 2.4), что при холодном старте может обернуться ошибками гонки.

Изменение 1 — маршрут /healthz. Проверяет не только «процесс жив», но и связь с БД: недоступная база должна вывести Pod из балансировки.

@app.route("/healthz")
def healthz():
    try:
        conn = get_db_connection()
        cur = conn.cursor()
        cur.execute("SELECT 1;")
        cur.close()
        conn.close()
        return jsonify({"status": "ok"}), 200
    except Exception:
        return jsonify({"status": "error"}), 503

Код 503 — важная деталь: readinessProbe считает не-2xx/3xx ответ провалом, и Kubernetes автоматически исключит Pod из Service, пока база не ответит.

Изменение 2 — advisory-lock в init_db(). Разобран в Приложении B.3:

ADVISORY_LOCK_ID = 424242

def init_db():
    conn = get_db_connection()
    try:
        cur = conn.cursor()
        cur.execute("SELECT pg_advisory_lock(%s);", (ADVISORY_LOCK_ID,))
        cur.execute("CREATE TABLE IF NOT EXISTS todos (id SERIAL PRIMARY KEY, task TEXT NOT NULL);")
        conn.commit()
        cur.execute("SELECT pg_advisory_unlock(%s);", (ADVISORY_LOCK_ID,))
        cur.close()
    finally:
        conn.close()

В воркерах Gunicorn и в initContainer init-db init_db() одинаково выполняется при импорте модуля — см. комментарий в коде и п. 2.4.

Отдельного Docker-HEALTHCHECK при этом не нужно: все проверки — кластерные, через пробы Kubernetes (см. п. 4.1).

Ключевые детали, на которые стоит обратить внимание:

  • volumes. static-volume — общий emptyDir, через который initContainer передаёт статику контейнеру nginx; nginx-config — тот самый ConfigMap: он подключается с subPath: nginx.conf в /etc/nginx/nginx.conf, то есть заменяет основной конфиг целиком, а не кладёт файл в /etc/nginx/conf.d/;
  • Service целим в порт 80 — трафик идёт через nginx, который проксирует всё на 127.0.0.1:5000. Напрямую порт 5000 наружу Service не открывает;
  • пробы обоих контейнеров идут на /healthz: у nginx запрос принимается на порт 80 и через proxy_pass уходит во Flask (замечание о таймаутах проб — в Приложении B.10).

Теперь то же самое по частям. Здесь находится главное исправление относительно исходных документов — initContainer init-static:

      volumes:
        - name: static-volume
          emptyDir: {}

      initContainers:
        - name: init-static
          image: local-todo-web:v1
          imagePullPolicy: Never
          command: ["sh", "-c", "cp -a /app/static/. /shared/ && ls -la /shared/"]
          volumeMounts:
            - name: static-volume
              mountPath: /shared

        - name: init-db
          image: local-todo-web:v1
          imagePullPolicy: Never
          command: ["python", "-c", "import app; app.init_db()"]
          env:
            - name: DB_HOST
              value: db-service
            - name: POSTGRES_DB
              value: todo_db
            - name: POSTGRES_USER
              value: postgres
            - name: POSTGRES_PASSWORD
              value: password

Что делает каждый:

  • init-static копирует статику из образа в общий emptyDir. Без него Nginx отдаёт 404 на /static/style.css — см. Приложение B;
  • init-db создаёт таблицу todos до запуска основных контейнеров. Если БД ещё не готова, процесс падает с ненулевым кодом, initContainer перезапускается с нарастающей паузой — и в итоге таблица будет создана.

Образ запускается с imagePullPolicy: Never: Kubernetes не должен пытаться скачать local-todo-web:v1 из интернета — он уже импортирован в кластер.

Пробы готовности для контейнера flask:

          readinessProbe:
            httpGet:
              path: /healthz
              port: 5000
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 5        # назначение см. в Приложении B.10
            failureThreshold: 6

Разница важна: readinessProbe решает, попадёт ли Pod в Service (то есть получит ли трафик), а livenessProbe — надо ли перезапустить контейнер. Маршрут /healthz в app.py проверяет не только «процесс жив», но и связь с БД, поэтому недоступная база корректно выведет Pod из балансировки.

4.6 Применение манифестов

Сначала разверните только базу данных и дождитесь её готовности:

kubectl apply -f k8s/01-postgres.yaml
kubectl wait --for=condition=Ready pod -l app=postgres --timeout=300s

Затем остальные манифесты:

kubectl apply -f k8s/

Зачем разбивать на два шага. Если применить всё сразу, поды web и postgres стартуют одновременно, и initContainer init-db начнёт подключаться к ещё не существующей базе. Некоторое время под будет в Init:Error / Init:BackOff, пока PostgreSQL не поднимется (initContainer перезапускается с нарастающей паузой и в итоге отрабатывает, но деплой занимает минуты вместо секунд).

Задержка здесь заметная ещё и потому, что PVC создаётся динамически: StorageClass local-path в k3s использует режим WaitForFirstConsumer, то есть том создаётся только в момент, когда его впервые запросит потребитель.

Раздельное применение избавляет от этой гонки и заодно даёт возможность сразу увидеть проблемы с базой, не замаскированные падением веб-подов.

Следить за запуском в реальном времени:

kubectl get pods -w

Дождаться, пока все поды перейдут в Running, и проверить:

kubectl get all | grep -E 'pod|service|deployment'
kubectl get ingress
curl -s http://localhost/healthz
curl -s -o /dev/null -w "style.css -> %{http_code}\n" http://localhost/static/style.css

Откройте http://localhost — приложение работает.

Проверка style.css -> 200 — это и есть проверка initContainer. Если видите 404, вернитесь к Приложению B.

Этап 5. Helm-чарт и Kubernetes Secrets

Цель: превратить набор манифестов в переиспользуемый чарт, вынести настройки в values.yaml и убрать пароли из кода манифестов.

5.1 Зачем нужен Helm

Манифесты k8s/*.yaml — это один конкретный вариант развёртывания. Helm даёт четыре возможности, которых нет у «голых» YAML-файлов:

  1. Шаблонизация. Значения вынесены в values.yaml, а не зашиты в манифесты — один чарт обслуживает любое окружение;
  2. Разделение окружений. Файлы values-dev.yaml / values-prod.yaml меняют конфигурацию, не трогая шаблоны (-f values-prod.yaml);
  3. Релизы и откат. Каждая установка/обновление — ревизия с историей, откат одной командой (разбирается на этапе 7);
  4. Сторонние решения. Готовые чарты из репозитория Artifact Hub устанавливаются одной командой.

5.2 Создание чарта

Чарт лежит в todo-app/todo-chart/. Если хотите создать его с нуля:

cd ~/todo-app
helm create todo-chart          # создаст шаблон-заготовку
rm -rf todo-chart/templates/*  # удаляем дефолтные шаблоны
rm -f  todo-chart/values.schema.json

Файлы Chart.yaml, values.yaml и templates/* уже подготовлены.

5.3 Из чего состоит чарт: как создаются его файлы

Разберём, откуда берутся файлы и что в каждом лежит.

Шаг 1 — каркас. Команда helm create todo-chart (см. 5.2) генерирует скелет: Chart.yaml, values.yaml, .helmignore и набор дефолтных шаблонов в templates/. Это заготовка для чужого приложения — шаблоны нам не подходят.

Шаг 2 — уборка. Дефолтные шаблоны удаляются (rm -rf todo-chart/templates/*), остаётся пустой каркас.

Шаг 3 — свои пять шаблонов. Каждый файл в templates/ — это тот же самый манифест из этапа 4 (k8s/*.yaml), в который вставлены три приёма Go-шаблонов:

  1. Имя ресурса через .Release.Name — чарт можно ставить несколько раз под разными именами без конфликтов (подробно — в 5.4):
metadata:
  name: {{ .Release.Name }}-web-service   # было: name: web-service
  1. Значения из values.yaml — вместо зашитых констант:
replicas: {{ .Values.web.replicaCount }}                 # было: replicas: 2
image: "{{ .Values.web.image.repository }}:{{ .Values.web.image.tag }}"
imagePullPolicy: {{ .Values.web.image.pullPolicy }}      # было: Never
storage: {{ .Values.postgres.storage }}                  # было: 1Gi
  1. Secret вместо паролей — там, где на этапе 4 стояло value: password, теперь ссылка на Secret, который создаёт шаблон secret.yaml (подробно — в 5.5):
env:
  - name: POSTGRES_PASSWORD
    valueFrom:
      secretKeyRef:
        name: {{ .Release.Name }}-db-secret
        key: postgres-password

.Release.Name подставляется из самой установки: helm install prod-todo ./todo-chart → все ресурсы названы prod-todo-*.

Шаг 4 — проверка. helm template prod-todo ./todo-chart печатает итоговый YAML — вы своими глазами видите «свой же этап 4» с подставленными значениями; helm lint --strict — контроль синтаксиса. Только после этого — helm install (см. 5.7).

При этом Chart.yaml почти не меняется (имя и версии), а values.yaml — единственное место, где меняется поведение чарта без правки шаблонов: это и есть первые три «возможности Helm» из 5.1 на практике.

5.7 Установка

Перед установкой нужно убрать «сырые» манифесты этапа 4, иначе имена ресурсов (web-service, db-service) совпадут с helm-релизом и в кластере окажутся дубликаты:

kubectl delete -f k8s/ --ignore-not-found

helm install prod-todo ./todo-chart --wait --timeout 10m
helm list
kubectl get all | grep prod-todo

Почему таймаут 10m, а не 5m. На свежем кластере при установке дают о себе знать две задержки: поды web и postgres тянут postgres:15-alpine и nginx:alpine с Docker Hub (в отличие от образа приложения, который импортирован k3d image import), и PVC создаётся только при первом потреблении (WaitForFirstConsumer). Суммарно до готовности может пройти 6–8 минут — и строгий --timeout 5m падает сообщением INSTALLATION FAILED: context deadline exceeded хотя деплой корректно завершится после (ресурсы остаются в кластере и дотягивают до 2/2). Если это случилось: убедитесь, что поды готовы (kubectl get pods -w), после чего приведите статус релиза в порядок — helm upgrade prod-todo ./todo-chart --wait (создаст новую ревизию со статусом deployed) либо свежий install после helm uninstall prod-todo.

Другой путь — прогрев образов: kubectl apply -f k8s/01-postgres.yaml + kubectl wait --for=condition=Ready pod -l app=postgres, как в 4.6, либо повторный запуск после первого вытягивания образов — тогда установка укладывается и в 5m.

Ожидаемое поведение: у init-db может быть 1–2 перезапуска. В отличие от этапа 4, где манифесты применялись по порядку, helm install отправляет в кластер все шаблоны чарта одной пачкой. Deployment с базой и Deployment с приложением стартуют одновременно, и init-db несколько раз попадает в ещё не готовую базу. Процесс падает с ненулевым кодом, Kubernetes перезапускает его с нарастающей паузой — и в итоге всё отрабатывает.

Проверить, что это ожидаемо, а не поломка:

# перезапуски считаются у initContainer, у основных контейнеров их быть не должно
kubectl get pod <имя-веб-пода> -o jsonpath='{.status.initContainerStatuses[*].name}{"\n"}{.status.initContainerStatuses[*].restartCount}'

Если поды не доходят до 2/2 Running или перезапуски идут единицами подряд — это уже настоящая проблема: kubectl logs <pod> -c init-db.

Проверка:

curl -s http://localhost/healthz
curl -s -o /dev/null -w "style.css -> %{http_code}\n" http://localhost/static/style.css

# посмотреть секрет (в base64) и убедиться, что он на месте
kubectl get secret prod-todo-db-secret -o jsonpath='{.data.postgres-password}' | base64 -d; echo

Этап 6. CI/CD через GitHub Actions

Цель: при каждом push в ветку main образ собирается, отправляется в реестр, чарт проверяется линтером и разворачивается в тестовый кластер k3d.

6.1 Почему нужен коммит-хэш, а не latest

Это один из ключевых вопросов лабораторной. Три причины:

  1. Kubernetes не увидит изменение. Если тег остался latest, значение поля image в манифесте не изменилось. Kubernetes считает спецификацию прежней и не инициирует RollingUpdate — поды продолжат работать на старом образе;
  2. Кэш на узлах. Узлы кэшируют latest и могут не скачать новую сборку, даже если Deployment обновился;
  3. Невозможен быстрый откат. При latest все сборки неразличимы — откатываться не на что.

Уникальный ${{ github.sha }} решает все три: меняется значение в манифесте, K8s делает RollingUpdate, а каждая ревизия Helm остаётся адресуемой.

6.2 Файл пайплайна

Готовый файл: todo-app/.github/workflows/deploy.yml. GitHub Actions ищет сценарии строго в .github/workflows/*.yml, путь не настраивается.

Этапы пайплайна:

Шаг Что делает
Checkout code клонирует репозиторий на раннер
Set up Helm ставит Helm нужной версии
Install k3d ставит k3d v5.9.0 — Docker и kubectl на раннере есть, а k3d нет
Detect application directory определяет, лежит ли проект в корне или в todo-app/
Python syntax check compileall — быстрый синтаксический контроль
Lint Helm Chart helm lint --strict ловит ошибки шаблонов до деплоя
Render Helm templates helm template — проверка, что шаблоны рендерятся
Log in to GHCR авторизация в ghcr.io через встроенный GITHUB_TOKEN
Build and push сборка и пуш образа с тегами :sha и :latest
Create k3d Cluster одноразовый кластер с пробросом порта 80
Deploy to Test Cluster helm install с --set для образа и pullPolicy
Verify Pods kubectl get pods -o wide
Smoke test реальные HTTP-запросы, включая проверку /static/style.css
Cleanup k3d Cluster if: always() — кластер удаляется даже при сбое

Обратите внимание на два исправления относительно исходного пайплайна:

  • web.image.pullPolicy=IfNotPresent. В values.yaml стоит Never (для локального кластера, куда образ импортирован через k3d image import). В CI образ приходит из GHCR, и при Never Kubernetes его не скачает — Pod зависнет в ErrImagePull. Значение pullPolicy должно совпадать у обоих initContainer'ов и основных контейнеров, иначе init-static упадёт первым;
  • if: always() на шаге очистки. Без этого при упавшем тесте кластер остался бы висеть до конца лимита раннера.

Откройте Actions → CI/CD Todo App и следите за шагами.

Первый прогон: ожидаемо падает задача Deploy to Test Cluster. Пакет в GHCR создаётся при первом пуше и по умолчанию приватный, поэтому кластер k3d на раннере анонимно скачать образ не сможет — поды зависнут в ErrImagePull, и helm install упадёт с context deadline exceeded. Это не дефект кода. В логах прогона появился шаг Diagnose failed pods (выполняется только при падении: печатает состояние подов и события) — убедитесь, что у подов web статус ErrImagePull, затем сделайте пакет публичным (см. 6.5) и нажмите Re-run failed jobs у этого прогона. Повторные пуши проблем не создают: пакет уже публичный.

6.5 Когда образ нужен из приватного реестра

По умолчанию GITHUB_TOKEN даёт права на push в GHCR, но кластер k3d на раннере анонимно скачать образ из приватного пакета не может. Если пакет приватный:

echo "${{ secrets.GITHUB_TOKEN }}" | kubectl create secret docker-registry regcred \
  --docker-server=ghcr.io \
  --docker-username=${{ github.actor }} \
  --docker-password=... \
  --namespace=default

Либо сделайте пакет публичным: в GitHub → Package → Package settings → Change visibility → Public. Для учебной работы этого достаточно.

Этап 6Б. CI/CD через GitFlic

Цель: повторить тот же конвейер на платформе GitFlic: при каждом push в ветку master образ собирается и отправляется в реестр проекта registry.gitflic.ru/project/varepo/todo-app, чарт проверяется линтером и разворачивается в тестовый кластер k3d на вашей же виртуалке.

Что уже должно быть. Этапы 0–5 пройдены на этой же VM (kubectl, k3d, helm лежат в ~/.local/bin, Docker работает) и установлен git. Java 17 и агент CI/CD ставятся в этом этапе. Файл конвейера уже лежит в проекте: todo-app/gitflic-ci.yaml (полный листинг — в 6Б.5); значения varepo/todo-app в нём и в командах ниже соответствуют проекту https://gitflic.ru/project/varepo/todo-app — для другого проекта замените путь на свой.

6Б.1 Чем GitFlic CI/CD устроен иначе

Идея пайплайна — та же, что в 6.1–6.2 (уникальный тег образа = sha коммита, линт до деплоя, smoke-тест HTTP запросами, очистка при любом исходе), но механика другая. Соответствие понятий:

GitHub Actions (этап 6) GitFlic CI/CD (этап 6Б)
.github/workflows/deploy.yml gitflic-ci.yaml в корне репозитория (путь настраивается в Настройки CI/CD проекта)
on: push: branches: [main] only: master на задаче (конвейер создаётся на ветке)
stages: = список jobs, внутри steps stages: + задачи, внутри scripts: (список shell-команд)
запускается на облачном раннере GitHub задача забирается агентом, зарегистрированным на вашей машине — облачных раннеров нет
permissions: packages: write + встроенный GITHUB_TOKEN транспортный токен профиля как пароль реестра (передаётся через маскируемую переменную проекта)
ghcr.io/<owner>/<image> registry.gitflic.ru/project/<владелец>/<проект>/<образ>
uses: docker/login-action@v4 обычная команда docker login в скрипте
if: always() на шаге очистки глобальный after_script: выполняется после каждой задачи независимо от её статуса
--timeout 5m на helm install тот же helm install --wait --timeout 10m (см. примечание в 5.7)

Две детали, на которых студенты обычно спотыкаются:

  1. Агент выполняет команды в вашей ОС. Для задачи типа shell нет «свежевыжатого» раннера из облака: всё, что требует конвейер (Docker, kubectl, k3d, helm), должно быть установлено на машине агента — поэтому этап 6Б и пишется под продолжение работы на той же виртуалке.
  2. helm install целиком зеркалит этап 6, но CI-кластер слушает порт 8088, а не 80: порт 80 на этой VM уже занят учебным кластером todo-cluster из этапов 4–5 (см. команду создания кластера в 6Б.5).

6Б.2 Компания и регистрация агента

Агент (runner) — программа, которая держит связь с GitFlic и выполняет задачи конвейера. Типы агентов: shell, powershell, docker, kuber; мы используем shell — он выполняет команды напрямую в операционной системе, то есть повторяет вашу рабочую среду этапов 4–5 без дополнительной изоляции (документация GitFlic считает такое использование допустимым для личных проектов).

Регистрация агента на gitflic.ru доступна только на уровне компании. Если компании ещё нет — создайте её (меню «Компании» → Создать компанию, имя на ваш вкус, например varepo-lab), затем откройте Настройки компании → Агенты CI/CD и оставьте вкладку открытой: из неё через минуту понадобится URL и токен регистрации.

Шаг 1 — Java 17. Агент — это Java-приложение (файлы .jar), начиная с версии runner 5.x требуется Java 17:

java --version                     # нужно "openjdk version 17.x" и старше
# если нет или версия ниже 17:
sudo apt install openjdk-17-jdk -y
java --version                     # теперь 17.x

Шаг 2 — скачивание агента. Дистрибутив публикуется в проекте gitflic/runner (страница Releases → последняя версия). Создайте рабочую директорию и скачайте два .jar-файла последнего релиза (на момент подготовки лабы — 5.1.2; ссылки ведут непосредственно на файлы релиза; UUID в ссылках у каждого релиза свои — если curl ответит 404, откройте страницу релиза в браузере и возьмите ссылки runner.jar / helper.jar из блока Files):

mkdir -p ~/gitflic-runner/{build,cache,log}
cd ~/gitflic-runner
curl -L -o runner.jar "https://gitflic.ru/project/gitflic/runner/release/467395fe-e2d1-4d31-bc02-cdb199abca2d/a5c80387-9301-498c-9510-c05a87881085/download"
curl -L -o helper.jar "https://gitflic.ru/project/gitflic/runner/release/467395fe-e2d1-4d31-bc02-cdb199abca2d/b95af713-ba5a-4775-b1f3-560858d59ca8/download"
ls -la *.jar       # runner.jar ~90 МБ, helper.jar ~13 МБ
file *.jar         # оба - "Java archive data (JAR)"

Шаг 3 — регистрация. Готовый агент нужно «привязать» к платформе и дать ему тег, по которому конвейер будет находить исполнителя. В веб-интерфейсе (Настройки компании → Агенты CI/CD) создайте агент и скопируйте URL и Token — они подставляются в команду регистрации:

cd ~/gitflic-runner
java -jar runner.jar register \
  --url <URL-из-настроек-компании> \
  --registration-token <Token-из-настроек-компании> \
  --name laba-kuber \
  --tags laba-kuber

После успешной регистрации в рабочей директории появится config/application.properties. Приведите его к виду (пути должны указывать на рабочую директорию агента в домашнем каталоге):

runner.executor=shell
runner.workingDir=/home/<ваш_пользователь>/gitflic-runner
runner.helperDir=/home/<ваш_пользователь>/gitflic-runner
logging.file.name=/home/<ваш_пользователь>/gitflic-runner/log/server.log
logging.level.root=INFO

В документации GitFlic агент ставят под отдельным системным пользователем (gitflic-runner) и сервисом systemd — правильная практика для многопользовательского сервера. Для учебной виртуалки достаточно запуска под своим пользователем: shell-агент выполняет задачи в изолированном контуре одной машины, а все нужные пайплайну инструменты уже стоят у вас в ~/.local/bin.

Шаг 4 — запуск. Откройте новый терминал (агент должен работать пока идёт конвейер) и запустите:

cd ~/gitflic-runner
java -jar runner.jar start --config=config/application.properties

Лог начнётся с ожидания заданий. Вернитесь в браузер на «Настройки компании → Агенты CI/CD»: агент laba-kuber должен появиться в списке со статусом активного. Именно этот агент будет брать задачи всех дальнейших конвейеров.

Этап 7. Очистка и Helm Rollback

Цель: научиться управлять жизненным циклом и откатывать неудачные релизы.

7.1 Полная очистка окружения

Выберите набор команд под текущий способ развёртывания:

# Docker Compose: остановить контейнеры
docker compose down
docker compose down -v        # с -v: удалить и тома (данные БД будут стёрты!)

# Манифесты из папки k8s/
kubectl delete -f k8s/

# Helm-релиз: удаляет все связанные Deployment, Service, ConfigMap, Secret, Ingress
helm uninstall prod-todo

# PVC удаляется отдельно: kubectl delete pvc prod-todo-postgres-pvc
# Helm не трогает PersistentVolumeClaim по умолчанию — это защита от потери данных

# Весь кластер вместе с балансировщиком и портами
k3d cluster delete todo-cluster

Порядок важен: сначала удаляются приложения, потом кластер. helm uninstall не удаляет PVC — это осознанное поведение, защищающее данные БД от случайной потери.

7.2 Просмотр истории релизов

helm history prod-todo

REVISION    UPDATED                      STATUS      CHART             APP VERSION  DESCRIPTION
1           Wed Oct  1 12:00:00 2026     superseded  todo-chart-0.1.0  1.0.0        Install complete
2           Wed Oct  1 12:10:00 2026     failed      todo-chart-0.1.0  1.0.0        Upgrade failed
3           Wed Oct  1 12:20:00 2026     deployed    todo-chart-0.1.0  1.0.0        Upgrade complete

Если после helm upgrade поды ушли в CrashLoopBackOff, а сайт перестал открываться, — история покажет, какая ревизия была последней рабочей.

7.3 Откат

helm rollback prod-todo 1

Что происходит под капотом:

  • Helm возвращает ConfigMap и Secret к значениям ревизии 1;
  • Deployment'у ставится образ из ревизии 1 (тот самый sha, который помог в п. 6.1);
  • Kubernetes выполняет RollingUpdate — старые поды живут, пока новые не пройдут readinessProbe.

Проверка результата:

helm history prod-todo      # появится ревизия 4 со статусом "Rollback to 1"
kubectl get pods
kubectl describe pod <имя-pod> | tail -20
curl -s http://localhost/healthz

7.4 Откат до «предыдущей» ревизии

helm rollback prod-todo            # без номера — откат на предыдущую
helm rollback prod-todo --dry-run # посмотреть, что изменится

Полезно знать: helm rollback тоже создаёт новую ревизию. Поэтому «откат отката» — это helm rollback prod-todo 3, а не повторная команда без номера.

Приложение A. Headlamp (веб-интерфейс кластера)

Headlamp — стандартный проект Kubernetes SIG UI, пришедший на смену заброшенному OpenLens. Ниже — способ, проверенный на практике: Headlamp разворачивается прямо в кластер Helm-чартом, а доступ к нему идёт через SSH-туннель. Это заметно проще, чем вариант с настольным приложением и переносом ~/.kube/config (он описан в разделе A.5).

A.1 Установка Headlamp в кластер

helm repo add headlamp https://kubernetes-sigs.github.io/headlamp/
helm repo update

helm install headlamp headlamp/headlamp \
  --namespace headlamp --create-namespace \
  --set service.type=NodePort \
  --set service.nodePort=30446 \
  --wait --timeout 4m

Проверка:

kubectl get pods -n headlamp      # headlamp-xxxx  1/1  Running
helm list -A | grep headlamp      # статус deployed

Установка в отдельный namespace headlamp удобна тем, что при удалении (helm uninstall headlamp -n headlamp) не затрагиваются ресурсы приложения.

A.2 Проброс порта

kubectl port-forward -n headlamp svc/headlamp 4466:80

Почему именно порт 4466 — важно. Фронтенд Headlamp жёстко запрашивает свою плагинальную часть по адресу http://localhost:4466. Если открыть интерфейс на другом порту (например, 30446), то origin страницы будет http://localhost:30446, а запрос уйдёт на http://localhost:4466 — браузер заблокирует его ошибкой CORS:

Access to fetch at 'http://localhost:4466/plugins' from origin
'http://localhost:30446' has been blocked by CORS policy

Страница при этом загрузится, но останется пустой: ошибки видны только в консоли браузера (F12 → Console). Поэтому хостовый порт обязан быть 4466.

A.3 Доступ из браузера на Windows

На Windows-машине откройте SSH-туннель и держите его запущенным:

ssh -N -L 4466:localhost:4466 student@192.168.10.1

Затем откройте в браузере:

http://localhost:4466

Вход выполняется токеном — по нему уже проверено на практике. Headlamp запущен с -in-cluster, но начиная с версий чарта 0.4x аутентификация на каждом пользователе остаётся обязательной, поэтому при первом открытии появится форма с предложением вставить токен (окно Authenticate). Выпустите временный ServiceAccount-токен и вставьте его в поле входа:

# выпустить токен на 12 часов
kubectl create token headlamp --namespace headlamp --duration=12h

# сохранить в файл, чтобы скопировать без лишних символов (в токене ~900+
# байтов, вручную переносить неудобно — ниже ещё один путь через scp)
kubectl create token headlamp --namespace headlamp --duration=12h \
  > ~/headlamp-token.txt

# проверить, что токен рабочий, не открывая браузер
kubectl get --raw "/api/v1/namespaces/default/pods" \
  --token="$(cat ~/headlamp-token.txt)" | head -c 120

Токен — единственный способ входа: вставленный в форме Authenticate, он превращается в HttpOnly-cookie (headlamp-auth-main.0), и интерфейс работает до истечения --duration. Повторный вход — та же команда kubectl create token + повторная вставка.

Если Windows-машина и ВМ соединены по SSH, удобно забрать токен без копирования 940 с лишним символов вручную:

scp student@192.168.10.1:~/headlamp-token.txt $env:TEMP\headlamp-token.txt
Get-Content $env:TEMP\headlamp-token.txt -Raw | Set-Clipboard

Если после вставки токена в консоли появляется CORS с адресом http://clusters/main/set-token — браузер определился как Electron-based (Headlamp собирает //clusters/... как scheme-relative URL, и он уходит на чужой хост). В обычных Chrome/Firefox этого нет: фронтенд строит same-origin запросы к /clusters/main/set-token. Пользуйтесь для Headlamp обычным браузером.

Что такое ServiceAccount-токен. Это подписанный Kubernetes'ом JWT, в котором зашиты имя пользователя (system:serviceaccount:headlamp:headlamp) и его группы. Kubernetes проверяет подпись своим секретом и понимает, какие RBAC-права есть у этого ServiceAccount. Поэтому токен — это и есть «пароль» для доступа к API: утечка токена означает утечку прав. Срок жизни задаётся флагом --duration, и по умолчанию он невелик — в проде это защита.

Сравните с тем, как устроен пользователь в Kubernetes: он обычно не имеет пароля вовсе, а авторизуется внешним провайдером (OIDC) либо получает короткоживущий токен через kubectl proxy / kubectl port-forward.

A.6 Альтернатива: настольное приложение Headlamp

Вариант из исходных материалов — установить Headlamp Desktop на Windows и скормить ему ~/.kube/config. Он работает, но требует больше шагов, и главное — пересоздания кластера с TLS-SAN.

Пересоздайте кластер с TLS-SAN (IP виртуальной машины должен попасть в сертификат API-сервера, иначе будет ошибка проверки сертификата):

# узнать IP виртуалки (адаптер VirtualHost-Only)
ip -4 addr show | grep -oP '(?<=inet\s)\d+(\.\d+){3}'

k3d cluster delete todo-cluster
k3d cluster create todo-cluster \
  -p "80:80@loadbalancer" \
  --k3s-arg "--tls-san=192.168.56.101@server:*"

Замените 192.168.56.101 на свой IP. Разбор флага: --tls-san добавляет Subject Alternative Name в сертификат API-сервера, а @server:* указывает, что SAN действует для всех IP-адресов узла.

A.2 Узнайте порт API-сервера

k3d cluster list todo-cluster          # смотрите поле KubeAPI
# типичный вид: http://0.0.0.0:36479

A.3 Установка и настройка Headlamp

  1. Скачайте Headlamp Desktop с официального GitHub (kubernetes-sigs/headlamp, раздел Releases) на Windows;
  2. Скопируйте ~/.kube/config из Ubuntu на Windows (scp пользователь@192.168.56.101:~/.kube/config C:\Users\USER\.kube\config);
  3. Откопите файл в блокноте и замените адрес API-сервера:
server: https://127.0.0.1:36479        # было
server: https://192.168.56.101:36479    # стало: IP вашей Ubuntu

Остальные адреса в том же файле (proxy-url и адреса в clusters) замените аналогично — с 127.0.0.1 на IP виртуалки; 4. Запустите Headlamp и укажите путь к изменённому файлу конфигурации.

A.4 Альтернатива без переноса конфига

Если перенос конфигурации неудобен, пробросьте порт API-сервера и обратитесь из Windows напрямую:

# на Windows в PowerShell
ssh -L 36479:127.0.0.1:36479 пользователь@192.168.56.101

Затем в конфиге оставьте server: https://127.0.0.1:36479 — трафик пойдёт через SSH-туннель, и TLS-SAN настраивать не нужно.

Приложение B. Исправленные ошибки в исходных манифестах

В исходных документах было несколько ошибок, из-за которых приложение не работало бы «из коробки». Ниже — каждая из них и решение, применённое в готовых файлах.

B.1 emptyDir затирал статику (критично)

Симптом: /static/style.css отдаёт 404, страница без стилей.

Причина. В docker-compose.yaml статика работала благодаря именованному тому: Docker при первом подключении копирует в него содержимое /app/static из образа web. В Kubernetes emptyDir всегда пустой. Монтирование его на /app/static перекрывает директорию, и CSS, запечённый в образ, становится недоступен обоим контейнерам.

Решение. initContainer, который копирует файлы из образа в общий том до старта основных контейнеров:

      initContainers:
        - name: init-static
          image: local-todo-web:v1
          imagePullPolicy: Never
          command: ["sh", "-c", "cp -a /app/static/. /shared/ && ls -la /shared/"]
          volumeMounts:
            - name: static-volume
              mountPath: /shared

Порядок гарантируется: initContainer'ы выполняются последовательно, и только после успешного завершения всех из них стартуют основные контейнеры.

B.2 pullPolicy: Never ломал деплой в CI (критично)

Симптом: в пайплайне поды висят в ErrImagePull, деплой не проходит.

Причина. values.yaml содержит pullPolicy: Never — это верно для локального кластера, куда образ импортирован через k3d image import. Но в CI образ публикуется в ghcr.io, и Kubernetes с Never не будет его скачивать.

Решение. Переопределять pullPolicy в пайплайне:

helm install test-todo ./todo-chart \
  --set web.image.repository=$IMAGE_REPO \
  --set web.image.tag=${{ github.sha }} \
  --set web.image.pullPolicy=IfNotPresent \
  --wait --timeout 10m

Значение должно совпадать у обоих initContainer'ов, иначе init-static упадёт раньше основных контейнеров.

B.3 Гонка при инициализации таблицы (средняя)

Симптом: поды postgres и web стартуют одновременно; Flask не может подключиться к БД и падает в CrashLoopBackOff. Кроме того, четыре воркера Gunicorn выполняют CREATE TABLE параллельно.

Решение, часть 1 — retry-логика в app.py (по умолчанию 60 попыток по 2 секунды = 120 секунд ожидания) вместо жёстких 10 секунд исходника.

Решение, часть 2 — advisory-lock, защищающий CREATE TABLE от гонки:

ADVISORY_LOCK_ID = 424242

def init_db():
    conn = get_db_connection()
    try:
        cur = conn.cursor()
        cur.execute("SELECT pg_advisory_lock(%s);", (ADVISORY_LOCK_ID,))
        cur.execute("CREATE TABLE IF NOT EXISTS todos (id SERIAL PRIMARY KEY, task TEXT NOT NULL);")
        conn.commit()
        cur.execute("SELECT pg_advisory_unlock(%s);", (ADVISORY_LOCK_ID,))
        cur.close()
    finally:
        conn.close()

Решение, часть 3 — initContainer init-db, который создаёт таблицу до старта основных контейнеров.

B.4 Таблица todos с лишним полем title

Симптом: в исходных документах этапа 1 таблица создавалась как id, title, task, где task TEXT NOT NULL, а title — TEXT без NOT NULL. Любой INSERT INTO todos (task) ... работал, но поле title всегда было NULL, а шаблон первого этапа рендерил {{ todo }} — то есть печатал целый кортеж (3, None, 'Купить молоко') вместо текста задачи.

Решение. Схема приведена к id, task с этапа 1, а в шаблоне везде используется {{ todo[1] }}.

B.5 depends_on без учёта готовности сервиса (средняя)

Симптом: при первом запуске web падает — БД ещё не инициализирована.

Решение. healthcheck для PostgreSQL и условие в depends_on:

  db:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d todo_db"]
  web:
    depends_on:
      db:
        condition: service_healthy

B.6 Редирект с кодом 302 вместо 303 после POST

Симптом: теоретически браузер мог бы повторить POST при возврате назад.

Решение. redirect(url_for("index"), code=303) — код 303 гарантирует переход методом GET и не повторяет POST.

B.7 Дублирующийся заголовок Cache-Control

Симптом: в ответе на /static/style.css два заголовка Cache-Control подряд; поведение браузеров не определено.

Причина. Директива expires 30d сама добавляет Cache-Control: max-age=2592000, а рядом стоял ещё и add_header Cache-Control "public, no-transform";.

Решение. Оставлен только expires 30d.

B.8 Deployment с RWO-PVC без Recreate

Симптом: после обновления кластера под PostgreSQL зависает в Terminating — Pod не может переехать на другой узел, пока старый не освободил том.

Решение. strategy: Recreate для обоих Deployment'ов PostgreSQL.

B.9 Отсутствие очистки кластера в пайплайне

Симптом: при упавшем тесте кластер k3d остаётся на раннере и расходует лимит часов.

Решение. Шаг Cleanup k3d Cluster с if: always().

B.10 Слишком короткий timeoutSeconds у проб

Симптом: в событиях кластера периодически появляются предупреждения, хотя приложение работает:

Warning  Unhealthy  Readiness probe failed: Get "http://10.42.0.19:80/":
         context deadline exceeded (Client.Timeout exceeded while awaiting headers)
Warning  Unhealthy  Liveness probe failed: Get "http://10.42.0.19:5000/healthz":
         context deadline exceeded (Client.Timeout exceeded while awaiting headers)

Причина. Поле timeoutSeconds в Kubernetes по умолчанию равно 1 секунде. Наша проба /healthz ходит не в «пустой» процесс, а по цепочке nginx → flask → PostgreSQL. Одной секунды не хватает при любом кратковременном замедлении, поэтому проба объявляет живое приложение неготовым.

Чем это опасно. Для readinessProbe последствие только шум в логах — под просто исключается из балансировки. Но для livenessProbe провал означает перезапуск контейнера. Слишком агрессивный таймаут убивает живое, но занятое приложение по кругу — это классический способ положить сервис в production.

Решение. Развести таймауты по назначению:

# readiness: готов ли принимать трафик — терпим к кратковременным сбоям
readinessProbe:
  httpGet: { path: /healthz, port: 5000 }
  initialDelaySeconds: 5
  periodSeconds: 5
  timeoutSeconds: 5          # было 1 (по умолчанию)
  failureThreshold: 6

# liveness: жив ли процесс — при провале контейнер перезапустят,
# поэтому таймаут щедрее
livenessProbe:
  httpGet: { path: /healthz, port: 5000 }
  initialDelaySeconds: 60
  periodSeconds: 20
  timeoutSeconds: 10         # было 1 (по умолчанию)
  failureThreshold: 6

У контейнера nginx проба идёт через прокси к Flask, поэтому там тоже timeoutSeconds: 5.

Важно отличать от нормы. Во время RollingUpdate у уходящих подов события connection refused и connection reset by peer — это ожидаемо: под завершается, а kubelet продолжает слать пробы. Смотрите события только по новым подам:

kubectl get events | grep <имя-нового-пода> | grep -i unhealthy
