Лабораторная работа. ToDo-приложение.¶

Compose → Kubernetes (k3d) → Helm → CI/CD¶

Стек: Python/Flask + PostgreSQL + Nginx
Среда выполнения: Ubuntu 24.04 в VirtualBox
Ожидаемый результат: работающее приложение, развёрнутое тремя способами, с автоматическим пайплайном CI/CD

Содержание¶

Заход 1 (локально на виртуалке): этапы 0–5 и 7 — всё разворачивается вручную и проверяется в браузере и через curl. Требуются только Docker, kubectl, k3d и Helm. 0.5 Установка Helm¶

Helm нужен начиная с этапа 5, но ставить его нужно здесь — на этапе 5 он уже должен быть в системе.

curl -fsSL -o /tmp/get_helm.sh https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3
chmod 700 /tmp/get_helm.sh
sudo /tmp/get_helm.sh
sudo rm -f /tmp/get_helm.sh
helm version --short

Официальный установщик кладёт бинарник в /usr/local/bin. Если система ругается на права, удалите старый файл и поставьте заново: sudo rm -f /usr/local/bin/helm && sudo /tmp/get_helm.sh.

Альтернативный способ — вручную, без установщика:

curl -fsSL -o /tmp/helm.tar.gz https://get.helm.sh/helm-${HELM_VER}-linux-amd64.tar.gz
tar -xzf /tmp/helm.tar.gz -C /tmp
sudo install -m 755 /tmp/linux-amd64/helm /usr/local/bin/helm
rm -rf /tmp/helm.tar.gz /tmp/linux-amd64

Этап 1. Docker Compose: Flask + PostgreSQL + Nginx¶

Цель: собрать минимальное приложение из трёх контейнеров и запустить его локально.

Создайте папку проекта и поддиректории:

mkdir -p ~/todo-app/app ~/todo-app/nginx
cd ~/todo-app

1.1 Зависимости Python¶

app/requirements.txt:

Flask==3.0.3
psycopg2-binary==2.9.9

1.2 Код приложения¶

app/app.py:

import os
import time

import psycopg2
from flask import Flask, redirect, render_template_string, request, url_for

app = Flask(__name__)

DB_HOST = os.environ.get("DB_HOST", "db")
DB_NAME = os.environ.get("POSTGRES_DB", "todo_db")
DB_USER = os.environ.get("POSTGRES_USER", "postgres")
DB_PASSWORD = os.environ.get("POSTGRES_PASSWORD", "password")


def get_db_connection():
    """Подключается к БД, повторяя попытку, пока база поднимается."""
    for _ in range(30):
        try:
            return psycopg2.connect(
                host=DB_HOST, database=DB_NAME, user=DB_USER, password=DB_PASSWORD
            )
        except psycopg2.OperationalError:
            time.sleep(2)
    raise Exception("Не удалось подключиться к базе данных")


def init_db():
    conn = get_db_connection()
    cur = conn.cursor()
    cur.execute("""
        CREATE TABLE IF NOT EXISTS todos (
            id SERIAL PRIMARY KEY,
            task TEXT NOT NULL
        );
    """)
    conn.commit()
    cur.close()
    conn.close()


# На этом этапе шаблон лежит прямо в коде — на этапе 2 вынесем в файл.
HTML_TEMPLATE = """
<!DOCTYPE html>
<html lang="ru">
<head><meta charset="UTF-8"><title>ToDo List</title></head>
<body>
    <h1>Список задач</h1>
    <form action="/add" method="POST">
        <input type="text" name="task" placeholder="Новая задача..." required>
        <button type="submit">Добавить</button>
    </form>
    <ul>
        {% for todo in todos %}
            <li>{{ todo[1] }}</li>
        {% endfor %}
    </ul>
</body>
</html>
"""


@app.route("/")
def index():
    conn = get_db_connection()
    cur = conn.cursor()
    cur.execute("SELECT id, task FROM todos ORDER BY id DESC;")
    todos = cur.fetchall()
    cur.close()
    conn.close()
    return render_template_string(HTML_TEMPLATE, todos=todos)


@app.route("/add", methods=["POST"])
def add_todo():
    task = (request.form.get("task") or "").strip()
    if task:
        conn = get_db_connection()
        cur = conn.cursor()
        cur.execute("INSERT INTO todos (task) VALUES (%s);", (task,))
        conn.commit()
        cur.close()
        conn.close()
    # Обычная HTML-форма без JS: отвечаем редиректом, чтобы пользователь
    # увидел главную страницу с новой задачей.
    return redirect(url_for("index"), code=303)


if __name__ == "__main__":
    init_db()
    app.run(host="0.0.0.0", port=5000)

Важное отличие от исходных документов. Там обработчик /add возвращал jsonify(...), 201, а браузер после отправки обычной формы показывал пользователю сырой JSON вида {"status":"success"}. Здесь сразу сделан 303 See Other на главную — это корректное поведение для этапа без JavaScript. На этапе 2, когда появится AJAX, вернём JSON обратно.

1.3 Dockerfile¶

FROM python:3.11-slim

WORKDIR /app

COPY app/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ .

EXPOSE 5000

CMD ["python", "app.py"]

Пояснение к порядку команд: requirements.txt копируется и устанавливается первым, отдельно от кода приложения. Docker кэширует слои, поэтому при изменении app.py пересобирается только финальный COPY, а pip install берётся из кэша.

1.4 Конфигурация Nginx¶

nginx/nginx.conf:

events {}

http {
    server {
        listen 80;

        location / {
            proxy_pass http://web:5000;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }
    }
}

В исходных документах здесь была конструкция error_page 405 =200 /; с отдельным блоком location /add. Она — костыль: Flask отвечает на POST кодом 201, а не 405, поэтому error_page просто не срабатывал. Редирект из приложения (п. 1.2) решает задачу корректно.

1.5 Docker Compose¶

docker-compose.yml:

services:
  db:
    image: postgres:15-alpine
    container_name: todo-db
    environment:
      POSTGRES_DB: todo_db
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: supersecretpassword
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d todo_db"]
      interval: 5s
      timeout: 5s
      retries: 12
    restart: always

  web:
    build: .
    container_name: todo-web
    environment:
      DB_HOST: db
      POSTGRES_DB: todo_db
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: supersecretpassword
    depends_on:
      db:
        condition: service_healthy
    restart: always

  nginx:
    image: nginx:alpine
    container_name: todo-nginx
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    ports:
      - "80:80"
    depends_on:
      - web
    restart: always

volumes:
  postgres_data:

Два решения, которых не было в исходниках:

  • убрано поле version: '3.8' — в Docker Compose v2 оно помечено устаревшим и печатает предупреждение при каждом запуске;
  • depends_on: db: condition: service_healthy вместо простого списка — depends_on без условия означает лишь «старт контейнера», а не готовность сервиса. С healthcheck Compose дожидается реальной готовности PostgreSQL, поэтому приложение не падает на первой попытке подключения.

2.3 Код приложения¶

В app/app.py измените три места:

  1. Импорт — вместо render_template_string используем render_template (шаблон теперь берётся из app/templates/):
from flask import Flask, jsonify, render_template, request
  1. Маршрут / — рендерим файл, а не строку:
return render_template("index.html", todos=todos)
  1. Маршрут /add — возвращаем JSON, потому что теперь его вызывает JS:
@app.route("/add", methods=["POST"])
def add_todo():
    task = (request.form.get("task") or "").strip()
    if not task:
        return jsonify({"error": "Missing task"}), 400

    conn = get_db_connection()
    cur = conn.cursor()
    cur.execute("INSERT INTO todos (task) VALUES (%s);", (task,))
    conn.commit()
    cur.close()
    conn.close()
    return jsonify({"status": "success", "task": task}), 201

Удалите из файла константу HTML_TEMPLATE — она больше не используется.

2.4 Переход на Gunicorn¶

Dockerfile:

FROM python:3.11-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY app/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ .

EXPOSE 5000

CMD ["gunicorn", "--workers", "4", "--bind", "0.0.0.0:5000", \
     "--access-logfile", "-", "--error-logfile", "-", "app:app"]

Что здесь принципиально:

  • app:app — Gunicorn импортирует модуль app и берёт из него объект app; точки нет, потому что модуль называется app.py, как и сам пакет;
  • --access-logfile - и --error-logfile - — логи пишутся в stdout/stderr, а не в файлы. Это обязательное условие для docker logs и kubectl logs;
  • PYTHONUNBUFFERED=1 — иначе print() из приложения буферизуется и в логах появляется с задержкой;
  • --workers 4 — четыре процесса-воркера. Учтите следствие: init_db() при старте выполнится в каждом воркере, поэтому в финальной версии он защищён advisory-lock'ом (см. todo-app/app/app.py).

3.3 Nginx: маршрут на статику¶

nginx/nginx.conf:

events {}

http {
    include      /etc/nginx/mime.types;
    default_type application/octet-stream;

    server {
        listen 80;

        # Статику отдаёт сам Nginx, мимо Flask/Gunicorn.
        location /static/ {
            alias      /app/static/;
            expires    30d;
            access_log off;
        }

        location / {
            proxy_pass         http://web:5000;
            proxy_http_version 1.1;
            proxy_set_header   Connection "";
            proxy_set_header   Host              $host;
            proxy_set_header   X-Real-IP         $remote_addr;
            proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        }
    }
}

Ключевое слово — alias: оно отдаёт файлы напрямую из файловой системы контейнера, минуя Python. expires 30d добавляет браузеру заголовок кэширования, поэтому CSS скачивается один раз.

Тонкость с дублированием заголовков. В исходных документах здесь стояло expires 30d вместе с add_header Cache-Control "public, no-transform";. Nginx сам добавляет Cache-Control: max-age=2592000 от директивы expires, поэтому в ответе оказывалось два заголовка Cache-Control подряд. Поведение браузеров в таком случае не определено, поэтому в готовых файлах оставлен только expires.

  web:
    build: .
    environment:
      DB_HOST: db
      POSTGRES_DB: todo_db
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: supersecretpassword
    volumes:
      - static_volume:/app/static      # ← новое: отдаём содержимое наружу
    depends_on:
      db:
        condition: service_healthy
    restart: always

  nginx:
    image: nginx:alpine
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - static_volume:/app/static:ro   # ← тот же том, только на чтение
    ports:
      - "80:80"
    depends_on:
      - web
    restart: always

volumes:
  postgres_data:
  static_volume:                       # ← новое

Логика: содержимое /app/static есть в образе web, но контейнер nginx использует другой образ (nginx:alpine), где этой папки нет. Именованный том решает задачу — Docker при первом подключении копирует в него данные из образа-«источника». Поэтому важно, чтобы web стартовал раньше nginx.

Здесь рождается ошибка, которая всплывёт на этапе 4. Механизм именованных томов Docker Compose («скопировать содержимое из образа в пустой том») не существует в Kubernetes. Там emptyDir всегда пустой, и монтирование его на /app/static «затрёт» CSS, запечённый в образ. Разбор этого — в Приложении B.

3.5 Перезапуск и проверка¶

docker compose up -d --build

Важно: bind-mount требует перезапуска контейнера. Если вы изменили nginx/nginx.conf, то docker compose up -d --build пересоберёт образ web, но контейнер nginx останется Running — Compose не отслеживает изменение содержимого файлов, смонтированных через bind-mount. Правки в конфиг Nginx попадут внутрь только после рестарта:

docker compose restart nginx

Проверить, что подхватилась новая версия, можно так:

docker exec todo-nginx nginx -t        # синтаксис конфигурации
docker exec todo-nginx cat /etc/nginx/nginx.conf | grep -A3 location
  • http://localhost/ — страница работает;
  • http://localhost/static/style.css — отдаётся CSS;
  • DevTools → Network → запрос style.css должен иметь Status 200 и Content-Type: text/css от nginx, а в логах Gunicorn (docker compose logs web) обращения к /static/style.css отсутствуют. Это и есть признак того, что статику действительно отдал Nginx.

Этап 4. Развёртывание в Kubernetes в k3d¶

Цель: перенести ту же архитектуру в Kubernetes. Ключевое отличие от Docker Compose — вместо отдельных контейнеров web и nginx появляется один Pod с двумя контейнерами, разделяющими сетевой namespace и файловую систему.

Сначала доведите приложение до финального вида — скопируйте из todo-app/ папку app/, а также Dockerfile, docker-compose.yml, nginx/nginx.conf. Остановите Compose, чтобы он не занимал порт 80:

docker compose down          # без -v: тома сохраняются, данные БД не пропадут

4.1 Подготовка образа¶

Dockerfile дополнен утилитой curl для проверок готовности:

FROM python:3.11-slim

RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY app/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ .

EXPOSE 5000

HEALTHCHECK --interval=15s --timeout=5s --start-period=20s --retries=5 \
    CMD curl -fsS http://localhost:5000/healthz || exit 1

CMD ["gunicorn", "--workers", "4", "--bind", "0.0.0.0:5000", \
     "--access-logfile", "-", "--error-logfile", "-", "app:app"]

Сборка:

docker build -t local-todo-web:v1 .
docker images | grep local-todo-web

Разбор флагов: -t local-todo-web:v1 — имя образа и тег; точка в конце — «искать Dockerfile в текущей папке».

4.2 Создание кластера k3d¶

k3d cluster create todo-cluster -p "80:80@loadbalancer"
  • todo-cluster — имя кластера. В k3d v5.x по умолчанию создаётся одноузловой кластер: 1 server и 0 агентов, плюс вспомогательный контейнер serverlb (load balancer). Проверить состав:
k3d cluster list     # колонка AGENTS покажет 0/0
k3d node list

Нужны дополнительные узлы — укажите явно: k3d cluster create todo-cluster --servers 1 --agents 2 -p "80:80@loadbalancer". Учтите, что каждый агент — отдельный Docker-контейнер и расходует память; на машине с 4 ГБ без необходимости их добавлять не стоит. * -p "80:80@loadbalancer" — проброс порта 80 вашей машины на внутренний балансировщик (Ingress-контроллер Traefik). Без этого флага Ingress работать не будет.

Проверка:

k3d cluster list
kubectl get nodes
kubectl get pods -A          # в системных namespace уже работает traefik

4.3 Импорт образа в кластер¶

k3d image import local-todo-web:v1 -c todo-cluster

Кластер k3d — это Docker-контейнеры, у него собственное хранилище образов. Образ из вашего локального Docker сюда не виден, его нужно скопировать.

4.4 Манифесты Kubernetes¶

Все четыре файла готовы в папке todo-app/k8s/. Разберём их по назначению.

k8s/01-postgres.yaml — база данных¶

Три объекта в одном файле, разделённых ---:

  1. PersistentVolumeClaim postgres-pvc — запрос постоянного тома на 1 ГБ. В k3d роль локального хранилища играет local-path (StorageClass создаётся k3s автоматически), но мы указываем PVC явно — так переносимее;
  2. Deployment postgres-deployment — сам PostgreSQL. Поле strategy: Recreate важно: Pod с подключённым RWO-томом нельзя перенести на другой узел, пока старый ещё не освободил том;
  3. Service db-service — стабильный внутренний DNS-адрес (db-service:5432) для общения с БД. Тип ClusterIP означает «доступен только внутри кластера».

k8s/02-nginx-config.yaml — конфигурация Nginx¶

apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  nginx.conf: |
    worker_processes auto;
    events { worker_connections 1024; }

    http {
        include       /etc/nginx/mime.types;
        default_type  application/octet-stream;

        access_log /dev/stdout;
        error_log  /dev/stderr warn;

        server {
            listen 80;

            location /static/ {
                alias   /app/static/;
                expires 30d;
            }

            location / {
                proxy_pass         http://127.0.0.1:5000;
                proxy_http_version 1.1;
                proxy_set_header   Connection "";
                proxy_set_header   Host              $host;
                proxy_set_header   X-Real-IP         $remote_addr;
                proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
            }
        }
    }

Два ключевых отличия от Compose:

  • proxy_pass http://127.0.0.1:5000 вместо http://web:5000 — контейнеры Nginx и Flask находятся в одном Pod, значит делят сетевой namespace, и localhost указывает на соседний контейнер;
  • access_log /dev/stdout — логи в stdout, чтобы kubectl logs их видел (как и в PYTHONUNBUFFERED=1 для Flask).

k8s/03-web.yaml — приложение¶

Deployment web-deployment с replicas: 2 (два независимых Pod — нагрузка распределяется, и видно, что rolling update работает) и двумя контейнерами: flask и nginx.

Здесь находится главное исправление относительно исходных документов — initContainer init-static:

      volumes:
        - name: static-volume
          emptyDir: {}

      initContainers:
        - name: init-static
          image: local-todo-web:v1
          imagePullPolicy: Never
          command: ["sh", "-c", "cp -a /app/static/. /shared/ && ls -la /shared/"]
          volumeMounts:
            - name: static-volume
              mountPath: /shared

        - name: init-db
          image: local-todo-web:v1
          imagePullPolicy: Never
          command: ["python", "-c", "import app; app.init_db()"]
          env:
            - name: DB_HOST
              value: db-service
            # ... остальные параметры подключения к БД

Что делает каждый:

  • init-static копирует статику из образа в общий emptyDir. Без него Nginx отдаёт 404 на /static/style.css — см. Приложение B;
  • init-db создаёт таблицу todos до запуска основных контейнеров. Если БД ещё не готова, процесс падает с ненулевым кодом, initContainer перезапускается с нарастающей паузой — и в итоге таблица будет создана.

Образ запускается с imagePullPolicy: Never: Kubernetes не должен пытаться скачать local-todo-web:v1 из интернета — он уже импортирован в кластер.

Пробы готовности для контейнера flask:

          readinessProbe:
            httpGet:
              path: /healthz
              port: 5000
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 6

Разница важна: readinessProbe решает, попадёт ли Pod в Service (то есть получит ли трафик), а livenessProbe — надо ли перезапустить контейнер. Маршрут /healthz в app.py проверяет не только «процесс жив», но и связь с БД, поэтому недоступная база корректно выведет Pod из балансировки.

k8s/04-ingress.yaml — внешний доступ¶

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: todo-ingress
  annotations:
    ingress.kubernetes.io/ssl-redirect: "false"
spec:
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80

Поле host не указано намеренно: в k3d нет DNS для вашего домена, поэтому срабатывает правило по умолчанию, и трафик принимается на любой Host-заголовок. Именно поэтому в браузере достаточно http://localhost.

4.5 Применение манифестов¶

Сначала разверните только базу данных и дождитесь её готовности:

kubectl apply -f k8s/01-postgres.yaml
kubectl wait --for=condition=Ready pod -l app=postgres --timeout=300s

Затем остальные манифесты:

kubectl apply -f k8s/

Зачем разбивать на два шага. Если применить всё сразу, поды web и postgres стартуют одновременно, и initContainer init-db начнёт подключаться к ещё не существующей базе. Некоторое время под будет в Init:Error / Init:BackOff, пока PostgreSQL не поднимется (initContainer перезапускается с нарастающей паузой и в итоге отрабатывает, но деплой занимает минуты вместо секунд).

Задержка здесь заметная ещё и потому, что PVC создаётся динамически: StorageClass local-path в k3s использует режим WaitForFirstConsumer, то есть том создаётся только в момент, когда его впервые запросит потребитель.

Раздельное применение избавляет от этой гонки и заодно даёт возможность сразу увидеть проблемы с базой, не замаскированные падением веб-подов.

Следить за запуском в реальном времени:

kubectl get pods -w

Дождаться, пока все поды перейдут в Running, и проверить:

kubectl get all | grep -E 'pod|service|deployment'
kubectl get ingress
curl -s http://localhost/healthz
curl -s -o /dev/null -w "style.css -> %{http_code}\n" http://localhost/static/style.css

Откройте http://localhost — приложение работает.

Проверка style.css -> 200 — это и есть проверка initContainer. Если видите 404, вернитесь к Приложению B.

Этап 5. Helm-чарт и Kubernetes Secrets¶

Цель: превратить набор манифестов в переиспользуемый чарт, вынести настройки в values.yaml и убрать пароли из кода манифестов.

5.1 Зачем нужен Helm¶

Манифесты k8s/*.yaml — это один конкретный вариант развёртывания. Helm даёт четыре возможности, которых нет у «голых» YAML-файлов:

  1. Шаблонизация. Значения вынесены в values.yaml, а не зашиты в манифесты — один чарт обслуживает любое окружение;
  2. Разделение окружений. Файлы values-dev.yaml / values-prod.yaml меняют конфигурацию, не трогая шаблоны (-f values-prod.yaml);
  3. Релизы и откат. Каждая установка/обновление — ревизия с историей, откат одной командой (разбирается на этапе 7);
  4. Сторонние решения. Готовые чарты из репозитория Artifact Hub устанавливаются одной командой.

5.2 Создание чарта¶

Чарт лежит в todo-app/todo-chart/. Если хотите создать его с нуля:

cd ~/todo-app
helm create todo-chart          # создаст шаблон-заготовку
rm -rf todo-chart/templates/*  # удаляем дефолтные шаблоны
rm -f  todo-chart/values.schema.json

Файлы Chart.yaml, values.yaml и templates/* уже подготовлены.

5.3 Имена ресурсов через .Release.Name¶

Каждый объект в шаблонах называется через {{ .Release.Name }}:

metadata:
  name: {{ .Release.Name }}-web-service

Это значит, что один и тот же чарт можно установить в кластер несколько раз под разными именами — prod-todo и stage-todo — без конфликтов имён. Ценное свойство: один чарт обслуживает несколько окружений.

5.4 Secret вместо пароля в манифесте¶

todo-chart/templates/secret.yaml:

apiVersion: v1
kind: Secret
metadata:
  name: {{ .Release.Name }}-db-secret
type: Opaque
data:
  postgres-db: {{ .Values.postgres.dbName | b64enc | quote }}
  postgres-user: {{ .Values.postgres.user | b64enc | quote }}
  postgres-password: {{ .Values.postgres.password | b64enc | quote }}

Использование в postgres.yaml и web.yaml:

          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: {{ .Release.Name }}-db-secret
                  key: postgres-password

Важно понимать честно: b64enc — это кодирование Base64, а не шифрование. Любой, кто прочитает Secret через API, декодирует его одной командой. Реальная защита — RBAC-права на Secret и хранение паролей в CI/CD-переменных, а не в Git. В этой лабораторной пароль учебный.

Шаблон Объекты

5.6 Установка¶

Перед установкой нужно убрать «сырые» манифесты этапа 4, иначе имена ресурсов (web-service, db-service) совпадут с helm-релизом и в кластере окажутся дубликаты:

kubectl delete -f k8s/ --ignore-not-found

helm install prod-todo ./todo-chart --wait --timeout 5m
helm list
kubectl get all | grep prod-todo

Ожидаемое поведение: у init-db может быть 1–2 перезапуска. В отличие от этапа 4, где манифесты применялись по порядку, helm install отправляет в кластер все шаблоны чарта одной пачкой. Deployment с базой и Deployment с приложением стартуют одновременно, и init-db несколько раз попадает в ещё не готовую базу. Процесс падает с ненулевым кодом, Kubernetes перезапускает его с нарастающей паузой — и в итоге всё отрабатывает.

Проверить, что это ожидаемо, а не поломка:

# перезапуски считаются у initContainer, у основных контейнеров их быть не должно
kubectl get pod <имя-веб-пода> -o jsonpath='{.status.initContainerStatuses[*].name}{"\n"}{.status.initContainerStatuses[*].restartCount}'

Если поды не доходят до 2/2 Running или перезапуски идут единицами подряд — это уже настоящая проблема: kubectl logs <pod> -c init-db.

Проверка:

curl -s http://localhost/healthz
curl -s -o /dev/null -w "style.css -> %{http_code}\n" http://localhost/static/style.css

# посмотреть секрет (в base64) и убедиться, что он на месте
kubectl get secret prod-todo-db-secret -o jsonpath='{.data.postgres-password}' | base64 -d; echo

5.7 Обновление релиза¶

Измените число реплик в values.yaml или передайте параметр напрямую:

Этап 6. CI/CD через GitHub Actions¶

Цель: при каждом push в ветку main образ собирается, отправляется в реестр, чарт проверяется линтером и разворачивается в тестовый кластер k3d.

6.1 Почему нужен коммит-хэш, а не latest¶

Это один из ключевых вопросов лабораторной. Три причины:

  1. Kubernetes не увидит изменение. Если тег остался latest, значение поля image в манифесте не изменилось. Kubernetes считает спецификацию прежней и не инициирует RollingUpdate — поды продолжат работать на старом образе;
  2. Кэш на узлах. Узлы кэшируют latest и могут не скачать новую сборку, даже если Deployment обновился;
  3. Невозможен быстрый откат. При latest все сборки неразличимы — откатываться не на что.

Уникальный ${{ github.sha }} решает все три: меняется значение в манифесте, K8s делает RollingUpdate, а каждая ревизия Helm остаётся адресуемой.

6.2 Файл пайплайна¶

Готовый файл: todo-app/.github/workflows/deploy.yml. GitHub Actions ищет сценарии строго в .github/workflows/*.yml, путь не настраивается.

Этапы пайплайна:

Шаг Что делает
Checkout code клонирует репозиторий на раннер
Set up Helm ставит Helm нужной версии
Detect application directory определяет, лежит ли проект в корне или в todo-app/
Python syntax check compileall — быстрый синтаксический контроль
Lint Helm Chart helm lint --strict ловит ошибки шаблонов до деплоя
Render Helm templates helm template — проверка, что шаблоны рендерятся
Log in to GHCR авторизация в ghcr.io через встроенный GITHUB_TOKEN

Create k3d Cluster одноразовый кластер с пробросом порта 80
Deploy to Test Cluster helm install с --set для образа и pullPolicy
Verify Pods kubectl get pods -o wide
Smoke test реальные HTTP-запросы, включая проверку /static/style.css

Обратите внимание на два исправления относительно исходного пайплайна:

  • web.image.pullPolicy=IfNotPresent. В values.yaml стоит Never (для локального кластера, куда образ импортирован через k3d image import). В CI образ приходит из GHCR, и при Never Kubernetes его не скачает — Pod зависнет в ErrImagePull. Значение pullPolicy должно совпадать у обоих initContainer'ов и основных контейнеров, иначе init-static упадёт первым;
  • if: always() на шаге очистки. Без этого при упавшем тесте кластер остался бы висеть до конца лимита раннера.

Этап 7. Очистка и Helm Rollback¶

Цель: научиться управлять жизненным циклом и откатывать неудачные релизы.

7.1 Полная очистка окружения¶

Выберите набор команд под текущий способ развёртывания:

# Docker Compose: остановить контейнеры
docker compose down
docker compose down -v        # с -v: удалить и тома (данные БД будут стёрты!)

# Манифесты из папки k8s/
kubectl delete -f k8s/

# Helm-релиз: удаляет все связанные Deployment, Service, ConfigMap, Secret, Ingress
helm uninstall prod-todo

# PVC удаляется отдельно: kubectl delete pvc prod-todo-postgres-pvc
# Helm не трогает PersistentVolumeClaim по умолчанию — это защита от потери данных

# Весь кластер вместе с балансировщиком и портами
k3d cluster delete todo-cluster

Порядок важен: сначала удаляются приложения, потом кластер. helm uninstall не удаляет PVC — это осознанное поведение, защищающее данные БД от случайной потери.

7.2 Просмотр истории релизов¶

helm history prod-todo

REVISION    UPDATED                      STATUS      CHART             APP VERSION  DESCRIPTION
1           Wed Oct  1 12:00:00 2026     superseded  todo-chart-0.1.0  1.0.0        Install complete
2           Wed Oct  1 12:10:00 2026     failed      todo-chart-0.1.0  1.0.0        Upgrade failed
3           Wed Oct  1 12:20:00 2026     deployed    todo-chart-0.1.0  1.0.0        Upgrade complete

Если после helm upgrade поды ушли в CrashLoopBackOff, а сайт перестал открываться, — история покажет, какая ревизия была последней рабочей.

7.3 Откат¶

helm rollback prod-todo 1

Что происходит под капотом:

  • Helm возвращает ConfigMap и Secret к значениям ревизии 1;
  • Deployment'у ставится образ из ревизии 1 (тот самый sha, который помог в п. 6.1);
  • Kubernetes выполняет RollingUpdate — старые поды живут, пока новые не пройдут readinessProbe.

Проверка результата:

Полезно знать: helm rollback тоже создаёт новую ревизию. Поэтому «откат отката» — это helm rollback prod-todo 3, а не повторная команда без номера.

Приложение A. Headlamp (веб-интерфейс кластера)¶

Headlamp — стандартный проект Kubernetes SIG UI, пришедший на смену заброшенному OpenLens. Ниже — способ, проверенный на практике: Headlamp разворачивается прямо в кластер Helm-чартом, а доступ к нему идёт через SSH-туннель. Это заметно проще, чем вариант с настольным приложением и переносом ~/.kube/config (он описан в разделе A.5).

A.1 Установка Headlamp в кластер¶

helm repo add headlamp https://kubernetes-sigs.github.io/headlamp/
helm repo update

helm install headlamp headlamp/headlamp \
  --namespace headlamp --create-namespace \
  --set service.type=NodePort \
  --set service.nodePort=30446 \
  --wait --timeout 4m

Проверка:

kubectl get pods -n headlamp      # headlamp-xxxx  1/1  Running
helm list -A | grep headlamp      # статус deployed

Установка в отдельный namespace headlamp удобна тем, что при удалении (helm uninstall headlamp -n headlamp) не затрагиваются ресурсы приложения.

A.2 Проброс порта¶

kubectl port-forward -n headlamp svc/headlamp 4466:80

Почему именно порт 4466 — важно. Фронтенд Headlamp жёстко запрашивает свою плагинальную часть по адресу http://localhost:4466. Если открыть интерфейс на другом порту (например, 30446), то origin страницы будет http://localhost:30446, а запрос уйдёт на http://localhost:4466 — браузер заблокирует его ошибкой CORS:

Access to fetch at 'http://localhost:4466/plugins' from origin
'http://localhost:30446' has been blocked by CORS policy

Страница при этом загрузится, но останется пустой: ошибки видны только в консоли браузера (F12 → Console). Поэтому хостовый порт обязан быть 4466.

A.3 Доступ из браузера на Windows¶

На Windows-машине откройте SSH-туннель и держите его запущенным:

ssh -N -L 4466:localhost:4466 student@192.168.10.1

Затем откройте в браузере:

http://localhost:4466

Войти не требуется: Headlamp запущен с ключом -in-cluster и использует ServiceAccount кластера. Если всё же появится форма входа, выпустите временный ServiceAccount-токен и вставьте его в поле входа:

# выпустить токен на 12 часов
kubectl create token headlamp --namespace headlamp --duration=12h

# сохранить в файл, чтобы копировать без лишних символов
kubectl create token headlamp --namespace headlamp --duration=12h \
  > ~/headlamp-token.txt

# проверить, что токен рабочий, не открывая браузер
kubectl get --raw "/api/v1/namespaces/default/pods" \
  --token="$(cat ~/headlamp-token.txt)" | head -c 120

Если Windows-машина и ВМ соединены по SSH, удобно забрать токен без копирования 940 с лишним символов вручную:

scp student@192.168.10.1:~/headlamp-token.txt $env:TEMP\headlamp-token.txt
Get-Content $env:TEMP\headlamp-token.txt -Raw | Set-Clipboard

Что такое ServiceAccount-токен. Это подписанный Kubernetes'ом JWT, в котором зашиты имя пользователя (system:serviceaccount:headlamp:headlamp) и его группы. Kubernetes проверяет подпись своим секретом и понимает, какие RBAC-права есть у этого ServiceAccount. Поэтому токен — это и есть «пароль» для доступа к API: утечка токена означает утечку прав. Срок жизни задаётся флагом --duration, и по умолчанию он невелик — в проде это защита.

Сравните с тем, как устроен пользователь в Kubernetes: он обычно не имеет пароля вовсе, а авторизуется внешним провайдером (OIDC) либо получает короткоживущий токен через kubectl proxy / kubectl port-forward.

Приложение B. Исправленные ошибки в исходных манифестах¶

В исходных документах было несколько ошибок, из-за которых приложение не работало бы «из коробки». Ниже — каждая из них и решение, применённое в готовых файлах.

B.1 emptyDir затирал статику (критично)¶

Симптом: /static/style.css отдаёт 404, страница без стилей.

Причина. В docker-compose.yml статика работала благодаря именованному тому: Docker при первом подключении копирует в него содержимое /app/static из образа web. В Kubernetes emptyDir всегда пустой. Монтирование его на /app/static перекрывает директорию, и CSS, запечённый в образ, становится недоступен обоим контейнерам.

Решение. initContainer, который копирует файлы из образа в общий том до старта основных контейнеров:

      initContainers:
        - name: init-static
          image: local-todo-web:v1
          imagePullPolicy: Never
          command: ["sh", "-c", "cp -a /app/static/. /shared/ && ls -la /shared/"]
          volumeMounts:
            - name: static-volume
              mountPath: /shared

Порядок гарантируется: initContainer'ы выполняются последовательно, и только после успешного завершения всех из них стартуют основные контейнеры.

B.2 pullPolicy: Never ломал деплой в CI (критично)¶

Симптом: в пайплайне поды висят в ErrImagePull, деплой не проходит.

Причина. values.yaml содержит pullPolicy: Never — это верно для локального кластера, куда образ импортирован через k3d image import. Но в CI образ публикуется в ghcr.io, и Kubernetes с Never не будет его скачивать.

Решение. Переопределять pullPolicy в пайплайне:

helm install test-todo ./todo-chart \
  --set web.image.repository=$IMAGE_REPO \
  --set web.image.tag=${{ github.sha }} \
  --set web.image.pullPolicy=IfNotPresent \
  --wait --timeout 5m

Значение должно совпадать у обоих initContainer'ов, иначе init-static упадёт раньше основных контейнеров.

B.3 Гонка при инициализации таблицы (средняя)¶

Симптом: поды postgres и web стартуют одновременно; Flask не может подключиться к БД и падает в CrashLoopBackOff. Кроме того, четыре воркера Gunicorn выполняют CREATE TABLE параллельно.

Решение, часть 1 — retry-логика в app.py (по умолчанию 60 попыток по 2 секунды = 120 секунд ожидания) вместо жёстких 10 секунд исходника.

Решение, часть 2 — advisory-lock, защищающий CREATE TABLE от гонки:

ADVISORY_LOCK_ID = 424242

def init_db():
    conn = get_db_connection()
    try:
        cur = conn.cursor()
        cur.execute("SELECT pg_advisory_lock(%s);", (ADVISORY_LOCK_ID,))
        cur.execute("CREATE TABLE IF NOT EXISTS todos (id SERIAL PRIMARY KEY, task TEXT NOT NULL);")
        conn.commit()
        cur.execute("SELECT pg_advisory_unlock(%s);", (ADVISORY_LOCK_ID,))
        cur.close()
    finally:
        conn.close()

Решение, часть 3 — initContainer init-db, который создаёт таблицу до старта основных контейнеров.

B.4 Таблица todos с лишним полем title¶

Симптом: в исходных документах этапа 1 таблица создавалась как id, title, task, где task TEXT NOT NULL, а title — TEXT без NOT NULL. Любой INSERT INTO todos (task) ... работал, но поле title всегда было NULL, а шаблон первого этапа рендерил {{ todo }} — то есть печатал целый кортеж (3, None, 'Купить молоко') вместо текста задачи.

Решение. Схема приведена к id, task с этапа 1, а в шаблоне везде используется {{ todo[1] }}.

B.5 depends_on без учёта готовности сервиса (средняя)¶

Симптом: при первом запуске web падает — БД ещё не инициализирована.

Решение. healthcheck для PostgreSQL и условие в depends_on:

  db:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d todo_db"]
  web:
    depends_on:
      db:
        condition: service_healthy

B.6 Редирект с кодом 302 вместо 303 после POST¶

Симптом: теоретически браузер мог бы повторить POST при возврате назад.

Решение. redirect(url_for("index"), code=303) — код 303 гарантирует переход методом GET и не повторяет POST.

B.7 Дублирующийся заголовок Cache-Control¶

Симптом: в ответе на /static/style.css два заголовка Cache-Control подряд; поведение браузеров не определено.

Причина. Директива expires 30d сама добавляет Cache-Control: max-age=2592000, а рядом стоял ещё и add_header Cache-Control "public, no-transform";.

Решение. Оставлен только expires 30d.

B.8 Deployment с RWO-PVC без Recreate¶

Симптом: после обновления кластера под PostgreSQL зависает в Terminating — Pod не может переехать на другой узел, пока старый не освободил том.

Решение. strategy: Recreate для обоих Deployment'ов PostgreSQL.

B.9 Отсутствие очистки кластера в пайплайне¶

Симптом: при упавшем тесте кластер k3d остаётся на раннере и расходует лимит часов.

Решение. Шаг Cleanup k3d Cluster с if: always().

B.10 Слишком короткий timeoutSeconds у проб¶

Симптом: в событиях кластера периодически появляются предупреждения, хотя приложение работает:

Warning  Unhealthy  Readiness probe failed: Get "http://10.42.0.19:80/":
         context deadline exceeded (Client.Timeout exceeded while awaiting headers)
Warning  Unhealthy  Liveness probe failed: Get "http://10.42.0.19:5000/healthz":
         context deadline exceeded (Client.Timeout exceeded while awaiting headers)

Причина. Поле timeoutSeconds в Kubernetes по умолчанию равно 1 секунде. Наша проба /healthz ходит не в «пустой» процесс, а по цепочке nginx → flask → PostgreSQL. Одной секунды не хватает при любом кратковременном замедлении, поэтому проба объявляет живое приложение неготовым.

Чем это опасно. Для readinessProbe последствие только шум в логах — под просто исключается из балансировки. Но для livenessProbe провал означает перезапуск контейнера. Слишком агрессивный таймаут убивает живое, но занятое приложение по кругу — это классический способ положить сервис в production.

Решение. Развести таймауты по назначению:

# readiness: готов ли принимать трафик — терпим к кратковременным сбоям
readinessProbe:
  httpGet: { path: /healthz, port: 5000 }
  initialDelaySeconds: 5
  periodSeconds: 5
  timeoutSeconds: 5          # было 1 (по умолчанию)
  failureThreshold: 6

# liveness: жив ли процесс — при провале контейнер перезапустят,
# поэтому таймаут щедрее
livenessProbe:
  httpGet: { path: /healthz, port: 5000 }
  initialDelaySeconds: 60
  periodSeconds: 20
  timeoutSeconds: 10         # было 1 (по умолчанию)
  failureThreshold: 6

У контейнера nginx проба идёт через прокси к Flask, поэтому там тоже timeoutSeconds: 5.

Важно отличать от нормы. Во время RollingUpdate у уходящих подов события connection refused и connection reset by peer — это ожидаемо: под завершается, а kubelet продолжает слать пробы. Смотрите события только по новым подам:

kubectl get events | grep <имя-нового-пода> | grep -i unhealthy
